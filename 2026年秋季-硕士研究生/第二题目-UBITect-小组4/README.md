## 2. 工具介绍与项目地址

UBITect 是面向 Linux 内核的未初始化使用（Use-Before-Initialization，UBI）缺陷检测工具，将流敏感的类型限定符推断与欠约束符号执行相结合。前者生成候选告警，后者针对候选位置搜索可行路径，以兼顾分析效率与结果精度。

- 官方 GitHub：https://github.com/seclab-ucr/UBITect
- 官方使用与搭建说明：https://github.com/seclab-ucr/UBITect/blob/master/README.md
- 本次复现对象：项目提供的 `example/backlog.c` 教程。

## 4. 搭建说明

项目提供源码构建与 Docker 两种安装方式，具体依赖和构建步骤见官方 README。

项目包含的主要组件如下：

| 组件 | 作用 |
| --- | --- |
| `llvm/` | LLVM、Clang 与基本块标记插件 |
| `src/` | 类型限定符推断与候选告警生成实现 |
| `KLEE/` | 欠约束符号执行及约束求解相关实现 |
| `getbclist.py` | 标记基本块并生成 Bitcode 文件清单 |
| `path_verify.py` | 根据候选告警调用符号执行进行路径验证 |

运行前需要确认上述工具已经编译，并将 `path_verify.py` 中的 `home_path` 设置为本机 UBITect 项目根目录。不同机器的绝对路径需要相应调整。

## 5. 工具搭建与实验后的主要思考

### 5.1 静态分析与符号执行具有互补性

类型限定符推断适合先筛选潜在问题，符号执行再针对候选位置检查路径可行性。两阶段设计将较广泛的缺陷筛查与针对性的路径验证结合起来，也让我们认识到“生成告警”和“确认路径”是不同的分析结论。

### 5.2 路径约束使缺陷解释更加具体

仅指出某个变量可能未初始化，还不能完整解释问题如何发生。通过分析分支选择、跳过的赋值和实际使用位置，可以得到 `a = 0` 这一明确条件，并利用符号执行结果加以核对。这体现了数理逻辑中的命题条件、约束合取与可满足性判断在程序分析中的应用。

### 5.3 欠约束分析结果需要结合环境假设理解

以函数为入口的欠约束符号执行能够减少对完整运行环境的依赖，但其结论受到输入、指针及外部环境建模的影响。因此，确认可行路径后仍应检查分析假设；若进一步研究真实内核缺陷，还需要结合调用上下文和实际初始化条件验证。

### 5.4 复现不仅是执行命令，还需要保留证据

源码、Bitcode、候选告警、确认结果和终端日志构成了复现证据。工具链、脚本路径和旧产物也可能影响实验。今后应同时记录项目提交号、工具版本与环境修改，使结果更容易复查和复用。
