DrvHorn 实验结果与分析

实验日期：2026 年 10 月 19 日。

本文整理研究生任务中 DrvHorn 的三个代表性实验，从论文的验证方法出发，解释引用计数断言、求解器输出及其与 Linux 驱动源代码的对应关系。

1. 实验目标与范围

论文 Automatic Detection of Reference Counting Bugs in Linux Kernel Drivers 提出 DrvHorn，通过内核 API 建模、程序切片、断言插入和约束 Horn 子句（Constrained Horn Clauses，CHC）求解，检测驱动初始化失败路径中的引用计数错误。

本次选择作者提供的三类案例：

  1. 真实缺陷：tpm_bios_measurements_ops。
  2. 未发现缺陷：ged_driver。
  3. 已知误报：acpi_wmi_driver。

先完成三个代表性案例，并额外导出了中间 LLVM IR 和求解轨迹用于分析。随后在本机补跑了作者全部 17 个轻量平台驱动，结果见第 3.1 节。当前未运行论文的完整平台驱动基准，不能据此估计工具总体准确率、误报率或性能。

4. 论文中的引用计数断言

4.1 被验证的性质

引用计数记录一个对象被持有的引用数量。获取引用和释放引用通常需要配对，例如：

get_device(dev);  /* 获取一个引用 */
put_device(dev);  /* 释放一个引用 */

论文第 3.1 节关注的核心性质是：如果驱动初始化失败，这次初始化造成的引用计数变化应恢复平衡。初始化入口可以是平台驱动的 .probe，也可以是文件操作的 .open。

对于被跟踪对象 o，记进入和退出初始化时的计数分别为 r_in(o) 和 r_out(o)，则：

Δ(o) = r_out(o) - r_in(o)

初始化失败 ⇒ 对每个被跟踪对象 o，Δ(o) = 0

在只涉及获取与释放操作的简化情况下：

Δ(o) = 获取引用次数 - 释放引用次数

必须针对同一个对象判断平衡；给对象 A 获取一次引用、给对象 B 释放一次引用，并不能互相抵消。

初始化成功后，驱动可以持有引用，交给后续的关闭、移除或其他释放流程处理。因此，本实验检查的是失败出口的平衡性质，不能要求成功返回前也释放所有引用。

4.2 为什么 IR 中检查的是“等于 1”

本次导出的模型将相关 kref 初始化为 1，通过模型操作增加或减少计数。失败出口的检查等价于：

ret = initialization();
if (ret != 0) {
    assert(model_refcount == 1);
}

这里的 1 是模型的检查基准，表示相关操作应恢复到工具要求的平衡状态。它不是“所有真实内核对象的引用计数永远为 1”，也不是要求失败时所有对象计数都变成 0。

本地工具源码中的对应关系为：

功能 实现位置 对应逻辑
建模计数初始化 KernelSetup.cc，第 95 行 将模型计数设为 1
建模获取引用 KernelSetup.cc，第 114 行 加 1
建模释放引用 KernelSetup.cc，第 135 行 减 1
构造计数断言 AssertKrefs.cc，第 54 行 比较计数是否等于 1
文件打开失败进入检查 FileOperations.cc，第 101 行 调用 .open，非零返回进入失败出口
平台驱动初始化失败进入检查 Platform.cc，第 63 行 调用 .probe，非零返回进入失败出口

5. 求解结果的逻辑含义

DrvHorn 的分析过程可以概括为：

Linux 驱动 / LLVM bitcode
  → 内核 API 建模、切片、构造初始化入口
  → 在失败出口插入引用计数断言
  → SeaHorn 编码为约束 Horn 子句
  → Z3 求解错误状态是否可达
  → 输出 sat / unsat，并回到源码确认

求解器查询的是“能否到达断言失败”，而不是直接查询“程序是否安全”。概念上，其查询为：

是否存在路径 π 和对象 o，使得：
初始化沿 π 失败返回，并且 Δ(o) ≠ 0？

因此，结果含义为：

输出 正确解释
sat 在转换后的模型中，错误状态可达，存在一条候选反例路径；仍需源码确认
unsat 在当前模型和剩余检查范围内，错误状态不可达
unknown 求解器未能给出确定结论
超时 分析没有在设定时限内完成，不能当作安全结论

例如，下面是说明原理的 Horn 规则示意，并非本次运行导出的原始子句：

Reach(下一位置, r+1) ← Reach(当前位置, r) 且执行 get
Reach(下一位置, r-1) ← Reach(当前位置, r) 且执行 put
Bad ← Reach(失败出口, r) 且 r ≠ 1
query Bad

sat 表示存在可达的 Bad 状态。由于模型可能丢失真实代码中的约束关系，候选路径不一定在实际程序中可执行，这正是需要区分真实缺陷与误报的原因。

6. 真实缺陷案例：TPM

6.1 源代码中的问题

此案例对应论文附录 A.1。原始内核文件为 drivers/char/tpm/eventlog/common.c，本地副本是 TPM 源码。

tpm_bios_measurements_ops 将 .open 指向 tpm_bios_measurements_open()，将 .release 指向 tpm_bios_measurements_release()。

关键位置如下：

行号 语句或操作 作用
42 get_device(&chip->dev) 获取设备引用
46 err = seq_open(file, seqops) 打开序列文件，可能失败
47–50 if (!err) { ... } 只处理成功情况
52 return err 错误时直接返回
61 put_device(&chip->dev) 位于正常关闭的释放回调中

将源码中与问题相关的部分简化为：

get_device(&chip->dev);

err = seq_open(file, seqops);
if (!err) {
    seq = file->private_data;
    seq->private = chip;
}
return err;

如果 seq_open() 失败，前面获取的引用没有在错误返回前释放。此时 .open 本身已经失败，正常打开后关闭文件的 .release 回调不会替这条失败路径完成清理。因此，不能因为文件中存在 put_device() 就认为引用已经配对。

6.2 与引用计数断言和求解结果的对应

用模型计数表示这条错误路径：

步骤 操作 模型计数
1 进入初始化 1
2 get_device() 2
3 seq_open() 返回错误 2
4 .open 返回非零，进入失败检查 2
5 检查 model_refcount == 1 不成立

因此，存在一个净增引用未归还的失败路径，求解结果为 sat。

在 TPM 中间 IR，第 26607 行 中，drvhorn.fail 调用 drvhorn.assert_kref。后者的关键逻辑如下：

%2 = load i32, i32* %1, align 4
%3 = icmp eq i32 %2, 1
br i1 %3, label %ret, label %err

err:
  call void @verifier.error()
  unreachable

这段 IR 明确建立了源码引用计数与求解目标的联系：计数不等于 1，就到达 verifier.error()。导出运行的 求解轨迹 包含：

sat
main@get_device.exit.i.i.split
main@get_device.exit.i.i.split --> query!0

轨迹中的名称是优化后 IR 的位置，不能把它们直接视为完整的 C 源码调用栈；需要结合上述源码和计数模型还原含义。

6.3 已有修复与证据范围

Linux 修复提交 5d8e297 在失败分支补上释放操作：

if (!err) {
    seq = file->private_data;
    seq->private = chip;
} else {
    put_device(&chip->dev);
}

补充的 put_device() 正好对应失败路径中缺少的引用归还。此案例的证据链为：源码失败分支遗漏释放、模型断言可违反、工具输出 sat，且已有内核修复补齐该操作。

本次没有运行打补丁后的版本，所以不能把“修复后输出 unsat”列为已完成的实验结果。

6.4 把“源码—断言—求解结果”连成完整推导

检查对象与时机。 被检查的是 chip->dev 内嵌的 kref。原始 C 文件没有手写这条断言，它由 DrvHorn 添加。生成的 main 初始化该计数，并把其地址保存在 drvhorn.kref.struct.file_operations；调用 .open 后，只有返回值非零才调用 drvhorn.fail。失败检查再读出同一个地址，交给 drvhorn.assert_kref。因此，获取引用和最后检查关联的是同一个设备，而不是两个对象的计数混算。

相关入口见 TPM 模型 main，第 26555 行。其含义可写为以下等价伪代码；这不是原始内核 C 代码：

c_chip = 1;                         // 工具设置的模型基准
err = tpm_bios_measurements_open();  // 内部 get_device 使 c_chip 加 1
if (err != 0)
    assert(c_chip == 1);            // DrvHorn 添加的失败出口检查

源码路径如何给出断言反例。 选择源码第 42 行已经获取引用、第 46 行 seq_open 失败的路径，则 c_chip = 1 + 1 = 2；第 52 行直接错误返回，没有中间的 put，所以断言计算的是 2 == 1，结果为假。第 61 行的 put 属于另一个释放回调，不在这条打开失败的执行路径上，不能用它抵消这里的 get。

为什么求解器输出 sat。 后端 IR 第 28132 行 把检查变成：

%_11 = load i32, i32* %_10, align 4
%_12 = icmp eq i32 %_11, 1
call void @verifier.assume.not(i1 %_12)
call void @seahorn.fail()

assume.not 表示只保留比较不成立的执行。因此，求解器寻找的正是“失败返回且计数不等于 1”的路径。对于上述 c_chip = 2 的状态，该路径满足所有相关条件，能够执行到错误终点。实际 SMT 文件第 4296 行 查询该终点，输出 sat；本机重求解输出 保留了该结果。

将这一条路径概括为逻辑条件，就是 open_failed ∧ c_chip != 1。源码允许打开失败，又确实没有归还已经取得的引用，因此模型反例对应真实缺陷。

7. 未发现缺陷案例：GED

7.1 源代码入口

原始文件为 drivers/acpi/evged.c，本地副本是 GED 源码。ged_driver 在第 188 行将 .probe 指向第 141 行的 ged_probe()。

该函数主要分配驱动数据、遍历 ACPI 资源并保存驱动数据。在该入口的直接代码中，没有与 TPM 类似的显式 get_device() 后错误返回遗漏释放的结构。

7.2 为什么本次 unsat 需要谨慎解释

进一步检查发现，GED 日志 明确提示：

WARNING: no assertion was found so either program does not have assertions or frontend discharged them.

同时，GED 中间 IR，第 26432 行 中的失败检查函数已经为空：

define void @drvhorn.fail(%struct.platform_device.1459* %0) {
entry:
  ret void
}

这说明交给后续求解流程的模型中，没有剩余的引用计数断言。日志给出的可能性是原本没有相关断言，或断言已由前端处理；仅凭该日志不能进一步区分。

因此，本次结果应表述为：

GED 案例输出 unsat，与作者示例一致；但本次预处理后没有剩余的引用计数断言，因此其含义是当前检查模型没有可达的断言违反，不能扩大为已经证明整个 GED 驱动完全正确。

该案例说明，解读 unsat 不仅需要看求解结果，还需要确认验证条件是否实际保留到了求解阶段。

7.3 区分“初始化失败”与“引用计数断言失败”

GED 也使用“probe 失败时检查引用平衡”的通用验证目标，但本次最终模型没有保留下来的具体计数断言。因此，不能虚构一条实际存在的 assert(c == 1)，再宣称求解器对它证明了复杂不变量。

源码与模型的对应为：

原始源码操作 模型中的对应 是否意味着引用计数错误
第 146–148 行分配失败 ged_probe 可以返回 -12 只是初始化失败，不自动构成引用错误
第 150 行保存 &pdev->dev 地址赋值，不是 get_device 保存指针本身不增加引用计数
第 152–156 行资源解析失败 ged_probe 可以返回 -22 同样只是初始化失败
probe 返回非零 main 进入 drvhorn.fail 进入失败出口后，还要有被违反的断言才算告警
drvhorn.fail 只有 ret void 不会从该函数到达错误标记 本次没有剩余错误分支

例如，源码分配失败返回 -ENOMEM，验证入口确实会进入 fail。但是这里的 fail 是工具构造的“失败返回处理函数”，其名称不代表已经发生断言违反；它的函数体直接返回，没有调用 verifier.error()。

本机新导出的 GED 实际 SMT 文件 查询为：

(query false)

逻辑常量 false 不可能成立，因此 本机求解输出 为 unsat。这不是“probe 不会失败”，也不是“整个驱动永远安全”；它说明本次转换后的验证程序没有可达的引用计数错误。

8. 误报案例：WMI

8.1 源代码中的对象管理与清理

原始文件为 drivers/platform/x86/wmi.c，本地副本是 WMI 源码。acpi_wmi_driver 的 .probe 指向第 1450 行的 acpi_wmi_probe()。

该入口会创建设备并调用 parse_wdg()，其中涉及多对象、链表和错误清理。关键位置如下：

行号 操作 说明
1219 device_initialize(&wblock->dev.dev) 初始化设备对象
1330 device_add(&wblock->dev.dev) 尝试添加设备
1337 put_device(&wblock->dev.dev) 对应添加失败分支中的清理
1482 device_create(...) 创建 WMI 总线设备
1490 parse_wdg(wmi_bus_dev, acpi_device) 解析并创建相关对象
1499 device_unregister(wmi_bus_dev) 错误清理路径中的设备注销

这些位置说明源码存在相应清理结构，但仅仅看到清理调用，不能证明每一条实际路径上的对象关系和引用都正确。

8.2 本次求解观察

WMI 中间 IR，第 26954 行 中，失败出口调用两个模型存储检查函数：

call void @drvhorn.check_storage.struct.device.189()
call void @drvhorn.check_storage.custom.7()

模型中的 drvhorn.assert_kref 同样执行计数是否等于 1 的检查。导出的求解轨迹 为：

sat
main@_54
main@_54 --> main@_54
main@_54 --> main@acpi_wmi_probe.exit.i.split
main@acpi_wmi_probe.exit.i.split --> query!0

这表明转换后的模型存在到达错误查询的路径，但轨迹没有提供足以完整还原 C 源码执行的对象身份、计数值和分支条件。

8.3 为什么称为误报，初次分析能确定到什么程度

作者 README 的 Evaluation 部分 明确将 acpi_wmi_driver 作为“正确预期是 unsat，工具却输出 sat”的误报示例。本次结果与该描述一致。

论文第 4.4 节讨论了两类一般性误报来源：

  1. 程序切片忽略部分间接信息流，使原本有关联的条件或状态丢失联系。
  2. SeaHorn 对指针、别名和内存关系的保守抽象，使模型包含真实程序中不可执行的路径。

这些因素可以解释为什么模型有错误路径，而真实源码未必有相应缺陷。初次分析仅有前述简略轨迹，没有足够证据确定 WMI 具体丢失的约束。论文附录 B.1 具体分析的是 acer_platform_probe，不能将那个案例的根因直接套用到 WMI。后续收到的外部详细轨迹提供了补充证据，见第 8.4 节。

因此，初次分析可以确认“复现了作者标注的 WMI 误报”，不能仅凭 sat 将其当作新的真实引用泄漏。

8.4 外部材料交叉核查：一条具体的 WMI 虚假反例

随后对用户提供的 另一份实验材料压缩包（见核查记录） 进行了只读核查，没有执行其中脚本。材料中的三份案例 IR 与本机此前导出的文件逐字节相同，三份内核源码也逐字节相同；内核 bitcode 的 SHA-256 一致。因此，可以对照其详细反例解释同一份 WMI 验证模型。

外部记录已另行保存，避免与本机运行结果混淆：

  • 外部 WMI 详细轨迹
  • 外部实验结果
  • IR 一致性核查记录

核对得到如下路径：

轨迹行号 观察 含义
1505–1515 创建选中的 custom.7 模型对象，计数初始化为 1 建立受检查对象及其基准
1560–1588 创建相关分支选择失败，结果为 -5 没有走成功初始化和入链分支
1606–1615 链表头与 next 的符号地址均为 761，但非确定循环条件取 false，继续进入循环体 模型允许空链表进入注册遍历
1644–1673 从链表位置恢复对象地址，执行计数减 1，得到 0 模型在不应进入的循环体内执行 put
1730–1753 选择下标 0 的对象，读取计数 0，违反 count == 1 并到达 seahorn.fail 解释此次 sat 的具体触发过程

这里的地址数字是反例中的符号取值，不是真实内核运行时地址。

对应源代码第 1308–1314 行，候选对象创建失败后被释放并 continue，只有成功对象才执行 list_add_tail。第 1326 行的链表遍历不会把空链表头作为有效设备处理。然而，同一模型 IR 的第 26729 行 使用 verifier.nondetvalue.1() 决定是否进入循环，使模型允许空链表仍进入循环体；抽象内存的对象关联进一步让该次 put 影响受检查对象。

因此，新增证据支持一条具体误报解释：链表结束条件及对象关系在模型中没有得到完整保留，导致源码不可行的执行在模型中可行。该反例体现的是模型计数从 1 降至 0，而不是 TPM 那样的计数从 1 升至 2。

此结论来自对外部轨迹与本机相同 IR 的交叉核查。本机尚未独立重新生成这份详细轨迹，也未修正模型后进行对照求解；不能据此声称已经消除 WMI 的全部误报。

8.5 把“断言确实违反”与“反例在源码中不可行”分别解释

断言检查哪个对象。 WMI 的失败出口检查模型对象存储区。对于这份反例，选中的是 drvhorn.storage.custom.7 的下标 0，检查该对象内嵌设备的 kref。该地址由 第 27008 行开始的存储检查函数 计算，再传给 drvhorn.assert_kref。这不是仅检查父总线设备的计数。

检查过程可写成以下等价伪代码：

err = acpi_wmi_probe();
if (err != 0 && target_index != -1) {
    obj = storage_custom_7[target_index];
    assert(obj.device.kref == 1);
}

这是说明选中子对象检查的模型伪代码，省略了其他存储区检查。target_index == -1 表示没有选中对象，不能把“未选中对象”误写成对某个对象计数的证明。

为什么该模型得到 sat。 外部详细反例中的状态变化为：

步骤 路径条件与操作 选中对象的模型计数
1 生成选中的抽象对象 1
2 候选设备创建失败，未走成功入链分支 1
3 链表为空，但非确定条件选择继续进入注册循环 1
4 注册分支选择失败，对模型关联的对象执行 put 0
5 probe 非零返回，读取下标 0 对象的计数 0
6 比较 0 == 1 为假，进入错误标记

因此，这条模型路径违反的条件是 probe_failed ∧ c_selected != 1，具体为计数 0 不等于基准 1。它表示该模型路径多执行了一次释放，不能把所有 sat 都解释成“遗漏释放造成泄漏”。

本机新导出的 WMI 后端 IR 第 27389 行 同样显示读取计数、比较是否等于 1、通过 assume.not 保留比较失败的执行，然后调用 seahorn.fail()。实际 SMT 文件第 7894 行 查询：

(query main@acpi_wmi_probe.exit.i.split)

本机重求解输出 为 sat。这一步确认的是验证模型错误状态可达，不是确认原始源码存在同样的执行。

为什么这条 sat 路径不能映射为真实源码缺陷。 原始源码第 1308–1311 行在创建失败后 continue，绕过第 1314 行入链操作；第 1326 行遍历的是已入链对象。当反例中的链表为空时，真实链表循环应直接结束，不会执行第 1337 行的 put。

关键差异不是 put 语句本身，而是它的执行前提：源码要求先存在可遍历的链表元素，模型却允许链表为空仍进入循环体，并通过抽象对象关联改变受检查对象的计数。因此，模型中的 0 != 1 是一次真实的模型断言违反，但该执行被源码的链表条件排除；这解释了这条候选反例为何属于误报。

WMI 的详细取值仍引用外部轨迹；本节新增的本机独立证据是实际 CHC、后端 IR 和重求解结果。两类证据的来源不能混写。

9. 综合分析与结论

三个案例共同展示了从论文性质到工具输出，再回到源代码核查的过程：

案例 断言及模型情况 求解结果 源码分析后的结论
TPM 失败出口检查计数恢复基准；存在获取后未归还的路径 sat 对应真实的遗漏释放，已有修复
GED 本次预处理后无剩余引用计数断言 unsat 工具未报告错误；结论限于本次模型
WMI 模型检查对象存储中的计数；错误查询可达 sat 与作者已知误报一致；外部详细轨迹支持空链表仍进入循环的具体虚假反例

从论文方法的角度，本次实验支持以下认识：

  • 引用计数检查需要结合具体对象和控制流，尤其是失败出口，不能只统计源码中 get 与 put 的出现次数。
  • sat 表示模型中的错误状态可达，源码分析负责判断候选路径是否对应真实缺陷。
  • unsat 的意义取决于模型和实际保留的验证条件；没有剩余断言时，不能将结果解释为对整个驱动的全面证明。
  • 本次已复现三类代表性行为并补跑全部 17 个轻量平台驱动。外部详细轨迹支持一条具体 WMI 虚假反例；尚未完成论文完整基准、TPM 修复后对照运行、WMI 详细反例在本机重新生成，以及模型修正后对照求解。
