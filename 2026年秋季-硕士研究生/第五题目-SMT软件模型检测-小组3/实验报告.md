# 实验报告

## 基于 SMT 的软件模型检测四算法比较实验（CPAchecker/DeviceDriversLinux64）

**复现文献：** Dirk Beyer, Matthias Dangl, “SMT-based Software Model Checking: An Experimental Comparison of Four Algorithms”，VSTTE 2016。

---

## 摘要

本实验以 CPAchecker 桌面框架为平台，对四种基于 SMT 的软件模型检测算法进行对比：有界模型检测（BMC）、k-归纳（k-induction）、谓词抽象（Predicate Abstraction）和 Impact。实验从 SV-COMP 2016 的 Linux 设备驱动任务中选取 **22** 个程序，其中 **15** 个标记为 TRUE，**7** 个标记为 FALSE。每个程序分别由四种算法运行，共得到 **88** 次正式运行记录。

在 88 次运行中，**23** 次得到与任务预期一致的已决正确结论，具体为 15 次 TRUE 和 8 次 FALSE；65 次未得到明确结论。按算法统计，k-induction 与 Impact 各有 8 次正确结论，Predicate 有 4 次，BMC 有 3 次。未决结果以超时为主，共 30 次；其次为递归错误 15 次、外部内存限制 10 次、Java 堆不足 6 次、其他错误 2 次及 UNKNOWN 2 次。

本批次的结果支持以下边界性结论：BMC 在找违例任务上可给出正确 FALSE，但安全证明能力受有限展开限制；k-induction 与 Impact 在本批次并列获得最多的已决正确结论，但两者的已决任务并不完全相同；Predicate 与 Impact 在安全证明方面表现较集中。由于样本规模只有 22 个任务、工具版本和资源预算与原论文不同，本报告不将上述结果解释为对原论文中 4779 个任务结论的全量复现。

---

## 一、算法简介与实验设计

### 1.1 四种算法简介

**1. 有界模型检测（BMC）**  
BMC 将程序的状态迁移展开到一个有限深度，并对展开后的路径编码成 SMT 公式，以检查是否存在违反安全性质的执行路径。它通常能较快发现违例，但有限深度内不存在反例只能说明该深度安全，不能直接证明无界循环始终安全。

**2. k-归纳（k-induction）**  
k-归纳通过检查有限步基础情形和归纳步情形证明安全：若前 k 步安全且可以证明第 k+1 步仍满足性质，则可对后续循环执行归纳。实际应用中常需要辅助不变量加强归纳结论，因此不变量生成器的能力会影响证明效率。

**3. 谓词抽象（Predicate Abstraction）**  
谓词抽象使用一组逻辑谓词概括程序状态，通过抽象可达图忽略与性质关系较弱的具体变量取值。若抽象分析产生不可行的违例路径，算法会通过 CEGAR 和插值精化增加谓词，逐步提高精度直到给出结果。

**4. Impact**  
Impact 是一种惰性抽象算法，先以较粗的抽象公式探索控制流可达图，再在可能的违例路径上使用 Craig 插值计算状态公式，并通过覆盖与精化合并重复或已验证的状态。它可以减少全局谓词枚举，但覆盖和插值过程仍可能在复杂程序上产生较大开销。

四种算法共同点在于都可以把程序状态迁移和安全性质转化为 SMT 公式求解；主要差异在于 BMC 和 k-induction 偏向路径展开与归纳，谓词抽象和 Impact 偏向抽象精化与状态覆盖。

### 1.2 实验设计思路

本实验参考四算法比较论文的基本思路，在同一验证框架 CPAchecker 中比较不同软件模型检测机制，而不是比较不同验证工具。实验重点观察算法在相同任务、相同规约和相同资源限制下，是能发现违例、证明安全，还是因超时、内存或分析限制而未决。

实验设计包括以下几个方面：

1. 从设备驱动验证任务中选取 22 个程序，其中 TRUE 和 FALSE 标签的任务均有覆盖；
2. 对每个任务分别运行 BMC、k-induction、谓词抽象和 Impact，共得到 88 次运行；
3. 使用统一的不可达性规约、CPU 限制、内存限制和 MathSAT5 求解器；
4. 将输出与任务预期标签对照，只把一致的 TRUE 或 FALSE 计为已决正确；
6. 重点分析 T01 与 T02 等典型任务，比较算法在“找违例”和“证安全”上的不同表现，而不只依据平均耗时排名。

### 2.3 四种算法配置

| 算法 | 核心机理 |
|---|---|
| BMC | 将循环和状态迁移展开到有限深度，利用 SMT 求解器检查是否存在违例路径 |

## 三、统计口径

本实验采用如下判定规则：

- 输出为 `true` 且任务期望为 TRUE：计为已决正确；
- 输出为 `false` 且任务期望为 FALSE：计为已决正确；
- 输出与任务期望不一致：计为错误判定；
- `TIMEOUT`、外部内存限制、Java 堆不足、递归错误、普通错误和 `unknown`：计为未决；
- 平均 CPU 时间只针对已决正确的运行计算，不包含超时或错误运行。

该口径的优点是不会把未决状态误写成错误判定。缺点是少量任务的已决正确平均值不能代表算法在其全部任务上的平均性能。

## 六、典型案例分析

### 6.1 案例一：T01 的模块引用计数违例

T01 对应 DRBD 相关的设备驱动任务，期望结果为 FALSE。正式运行中，四种算法都给出与期望一致的 `false`：

| 算法 | 正式状态 | CPU 时间（秒） |
|---|---|---:|
| BMC | false（correct） | 157.577 |
| k-induction | false（correct） | 169.175 |
| Predicate | false（correct） | 13.100 |
| Impact | false（correct） | 14.691 |

BMC 的核心反例文本保存在 `cases/T01/bmc/cpa-output/Counterexample.1.core.txt`。其中关键轨迹可概括为：

1. 初始化模块引用计数，初值为 1；
2. 调用 DRBD 的 proc open 回调；
3. 调用 `ldv_try_module_get` 成立，使引用计数增加到 2；
4. 继续检查 proc open 的返回值；
5. open 操作的返回值不为 0；
6. 最终检查模块引用计数时发现其不等于 1；
7. 调用断言或错误位置，得到不可达性规约违例。

核心反例文件中可对应的关键源行包括 11073、11017、11076、10423 和 10345，分别涉及 open 回调、模块引用获取、失败返回值检查、最终状态检查和错误位置。

T01 的意义在于：

- 这是本批次唯一一个四种算法都成功判出 FALSE 的任务；
- 三种算法的结论一致，说明违例判定不是单个算法偶然猜测；
- 不同算法仍存在耗时差异：Predicate 和 Impact 分别为 13.100 秒和 14.691 秒，而 BMC 和 k-induction 均超过 150 秒；
- 它体现了短可达反例对违例发现的直接价值，也说明“小任务上四算法都能解出”不等于“在全部安全证明任务上也能解出”。

### 6.2 案例二：T02 的安全证明差异

T02 对应同一类 DRBD 安全任务，期望结果为 TRUE。正式结果如下：

| 算法 | 状态 | CPU 时间（秒） |
|---|---|---:|
| BMC | TIMEOUT | 1202.036 |
| k-induction | TIMEOUT | 901.588 |
| Predicate | true（correct） | 16.839 |
| Impact | true（correct） | 24.181 |

T02 中只有两种算法给出正确结论：

- Predicate 用 16.839 秒完成安全证明；
- Impact 用 24.181 秒完成安全证明；
- BMC 在 1202.036 秒 CPU 时间附近结束且未给出结论；
- k-induction 在 901.588 秒 CPU 时间附近结束且未给出结论。

该案例体现了证明安全与寻找违例的根本区别。BMC 主要通过有限展开判断有限长度内是否存在违例；若循环无界，有限展开不能替代对所有未来状态的证明，因此容易超时。k-induction 需要基础情形和归纳情形同时成立，并依赖足够强的辅助不变量。本批次中 k-induction 未能在资源限制内得到 T02 的结论。

Predicate 从谓词集合出发，通过抽象和反例精化寻找可行与不可行路径，并在收敛后证明安全。Impact 则以惰性抽象维护局部状态公式，在插值和覆盖过程收敛后证明安全。二者都属于抽象精化或插值精化路线，因此能够利用更强的状态描述完成本批次的 T02 安全证明。

该案例不能直接推广为“抽象算法永远优于 k-induction”，也不能仅凭一次超时断言某算法理论能力不足。它只能说明，在当前工具版本、任务结构和资源预算下，Predicate 与 Impact 更适合本批次的这类安全证明。

## 七、与原论文结论的对照

### 7.1 原论文与本次实验的差异

| 比较维度 | 原论文 | 本次实验 |
|---|---|---|
| 基准规模 | 4779 个任务 | 22 个任务 |
| 总运行规模 | 4×4779 | 88 次 |
| 执行环境 | 两台 2.6 GHz Xeon，135 GB 内存，Ubuntu 16.04 | Windows 11 + Docker，容器 Ubuntu 20.04.6 |
| CPAchecker | 1.6.8-vstte16 | 1.6.1-svn23022 |
| MathSAT5 | 原实验版本，文献中记录使用 | 5.3.12 |
| 单任务 CPU 限制 | 15 分钟 | 软限制 900 秒，硬限制 1200 秒 |
| 内存限制 | 15 GB | BenchExec 6000 MB、容器根上限 8 GiB |
| 分析目的 | 全量算法比较与分类分析 | 小规模复现、工程可核验与案例分析 |

因此，本报告中的数值只能用于本批次任务，不能直接作为原论文结果的全量复现。

### 7.2 对应关系

原论文强调：

- BMC 擅长快速发现违例，但证明安全能力较弱；
- k-induction 能在合适的不变量结构下证明大量安全任务；
- Predicate 与 Impact 的证明能力接近；
- 算法表现强烈依赖任务类别；
- 没有一种算法在所有任务上无条件优于其他算法。

本地结果与上述定性规律有一定对应：

- T01 是四算法都能发现违例的短反例案例；
- T02 是抽象类算法更能给出安全结论的案例；
- k-induction 在本批次安全任务上取得较多已决结果；
- Predicate 和 Impact 在部分安全任务上收敛；
- BMC 在本批次没有得到正确 TRUE。

两套实验不能直接用数量排名比较，因为任务集、版本、资源限制和工具实现都不相同。

## 八、实验局限

本实验存在以下限制：

1. **任务规模较小**：只使用 22 个任务，无法从统计上验证原论文的 4779 项结论。
2. **资源限制不同**：本实验的 BenchExec 内存限制为 6000 MB，容器根上限为 8 GiB，与原论文的 15 GB 不同。
3. **CPU 限制存在软硬两个边界**：软限制为 900 秒，硬限制为 1200 秒，超时状态不能直接视为算法永远无法求解。
4. **工具版本不同**：本地 CPAchecker 为 1.6.1-svn23022，与原论文使用的 1.6.8-vstte16 不一致。
5. **递归和内存问题影响可比性**：15 次递归错误和 16 次内存相关未决状态占运行总数较大比例。
6. **平均耗时只包含已决正确结果**：成功次数不相等时，平均值不能代表算法优劣。
7. **未进行统计显著性检验**：本次数据是描述性对照，没有进行配对假设检验或置信区间分析。
8. **只做了一次正式运行**：未进行重复运行，不能排除偶发性 I/O、机器负载或资源调度影响。

## 九、结论

本次实验对 22 个设备驱动任务进行 88 次正式验证，并得到 23 次与预期一致的已决正确结论、65 次未决结论。

主要结论如下：

1. T01 的违例在四种算法下都能被发现，说明短反例任务对不同算法的判定一致性较好。
2. k-induction 和 Impact 在本批次的已决正确数量相同，均为 8 次；k-induction 与部分安全证明关系较强，Impact 在本批次得到最多的正确 TRUE。
3. Predicate 的已决正确平均 CPU 最低，但成功数只有 4 次，不能据此对其总体性能排名。
4. BMC 在本批次只得到 3 次正确 FALSE，没有得到正确 TRUE，表现符合“擅长找违例、证明无界安全困难”的机理。
5. T02 是本批次最具代表性的算法差异：Predicate 和 Impact 证明 TRUE，BMC 和 k-induction 超时。
6. 实验结果依赖任务、工具版本和资源预算，没有一种算法在本批次的所有指标上占优。

因此，本次项目能够验证原论文中“没有全能算法、算法表现取决于任务特征”的核心经验，并提供可追溯的 T01、T02 案例与 88 次正式运行证据。由于任务规模和环境差异较大，本报告的结论应限定在“本地 22 个任务及当前资源预算”范围内。
