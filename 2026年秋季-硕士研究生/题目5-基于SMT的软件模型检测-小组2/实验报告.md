# SMT-based Software Model Checking：四算法在 DeviceDriversLinux64 上的复现实验

> 课程作业 · 复现 Beyer & Dangl, VSTTE 2016
> 实验日期：2026-11-02 · 工具：CPAchecker 1.6.1-svn（论文补充材料原版）+ MathSAT5

## 0. 摘要

本文在论文补充材料的原版 CPAchecker 1.6.1-svn 23022 + MathSAT5 上，复现了 VSTTE 2016 四种 SMT-based 软件模型检测算法在 Linux 驱动任务上的对比。从 SV-COMP 2016 DeviceDriversLinux64 的 2120 个任务中分层抽取 22 个，按论文 README 的四条命令各运行一次（共 88 次），在 Docker linux/amd64 容器中执行。结果：70 次给出 TRUE/FALSE 的运行全部与 ground truth 一致，88/88 次的 outcome 类别与论文完全一致；BMC 在 10 个安全任务上超时，k-induction 在 5 个指针密集任务上超时，谓词抽象与 Impact 各解 21/22，vhost 任务上仅 BMC 找到错误。报告还逐行解释了一条 LDV 调用顺序违规的错误轨迹，并以 npgtech 为例说明“BMC 无法证明 ∀k、k-induction/CEGAR 可以”的差异根源。

## 1. 实验问题与论文结论

论文用同一框架 CPAchecker、同一 SMT 求解器 MathSAT5，比较四种算法：

| 算法 | 核心机制 | 理论能力 |
|---|---|---|
| BMC | 循环展开 k 次，检查错误可达性 | 主要证伪；有界循环可经前向条件检查证安全，但无法证明无界安全 |
| k-induction | 基例（BMC）+ 归纳步（从循环头展开 k+1 次） | 可证明 k-归纳不变式；常需辅助不变式生成器 |
| 谓词抽象 | CEGAR + 显式谓词精度 + 插值细化 | 可证安全；急切计算抽象，重构次数少 |
| Impact（惰性抽象） | 无显式精度，按需 Expand/Refine，Craig 插值 | 惰性、错误发现快；安全证明可能需更多重构 |

论文全量 4779 任务上的正确结果：BMC 1024、k-induction 2482、谓词抽象 2325、Impact 2306；在 DeviceDriversLinux64 上谓词抽象与 Impact 略优于 k-induction，BMC 因大量无界循环而大量超时。

## 2. 实验方法

### 2.1 工具与运行环境（与论文的差异必须明说）

- 论文：Ubuntu 16.04 / OpenJDK 1.8 / 双路 Xeon E5-2650 v2 / 每任务 2 CPU 核、900s CPU、15GB 内存；正文称工具版本为 `cpachecker-1.6.8-vstte16`。
- 本实验：MacBook Air（Apple Silicon arm64，10 核，16GB，macOS 26.3.1）；Docker Desktop 29.2.1 以 `linux/amd64` 容器运行（容器内核 Linux 6.12，Temurin OpenJDK 1.8.0_504）。
- 工具版本：补充材料里的 `cpachecker.jar` 实际自报 **CPAchecker 1.6.1-svn 23022**；其 `NEWS.txt`/结果 CSV 元数据写 22870，论文正文写 1.6.8-vstte16。三处不一致，本报告以实际运行的 23022 为准。
- 为什么用容器：论文补充包只带 `lib/java/runtime/libmathsat5j.so`（Linux 原生库），macOS 无法加载 MathSAT5；容器是唯一能保持 “CPAchecker + MathSAT5” 组合的路径。
- 资源上限：**5000MB Java 堆 / 6000MB cgroup 内存 / 170s CPAchecker 内部时限 + 180s 外部兜底 / 单并发**。论文是 15GB、900s、2 核；本实验内存只有论文的 40%，超时只有 19%。
- 外层墙钟含容器/JVM 启动开销（约 3–4s）；结论中的运行时间采用 CPAchecker 自报的 `Total CPU time`。由于宿主 CPU、模拟层、核数限制与论文不同，绝对时间仍**不可**与论文逐秒对齐，只用于本实验内的横向比较与量级校验。冒烟测试（`example-safe.c`）总 CPU 2.79s，说明 MathSAT5 可正常加载并给出 TRUE。
- 未做 CPU 绑核；Docker VM 有 10 个虚拟核，CPAchecker 主要为单线程，但 GC/求解器可能用到多核。论文限制 2 核，故本实验在高并发/多线程场景下可能偏快。

### 2.2 任务集与抽样

- 数据源：SV-COMP 2016 `svcomp16` 标签，DeviceDriversLinux64 类别，共 2120 个任务。
- 属性：`ALL.prp` = `CHECK( init(main()), LTL(G ! call(__VERIFIER_error())) )`；所有任务加 `-64`。
- 抽样：**分层抽样 22 个**（非随机），五层：
  - A 四算法均证安全且快（6）
  - B 四算法均报错（5）
  - C2 BMC 超时、k-induction 证安全（5；谓词/Impact 也能证）
  - C4 仅谓词抽象/Impact 证安全（5）
  - C3 仅 BMC 找到错误（1）
- 抽样的目的：同时获得“可复现的一致性校验”和“算法分歧案例”；**不能**用这 22 个任务的比例估计整个类别。全类别比例见 §3.4（论文数据）。

### 2.3 四条命令

严格取自论文补充材料 README（`scripts/cpa.sh`）：

```bash
# BMC
-bmc -setprop solver.solver=MATHSAT5 \
-setprop cpa.predicate.encodeBitvectorAs=BITVECTOR \
-setprop cpa.predicate.encodeFloatAs=FLOAT \
-setprop analysis.checkCounterexamples=true -setprop counterexample.checker=CBMC \
-setprop cpa.bounds.maxLoopIterationsUpperBound=0 \
-setprop cpa.bounds.maxLoopIterations=1 \
-setprop cpa.bounds.maxLoopIterationAdjusterFactory=INCREMENT

# k-induction
-sv-comp16--k-induction

# 谓词抽象
-predicateAnalysis-PredAbsRefiner-ABEl-bitprecise \
-setprop cpa.predicate.encodeFloatAs=FLOAT \
-setprop analysis.checkCounterexamples=true -setprop counterexample.checker=CBMC

# Impact
-predicateAnalysis-ImpactRefiner-ABEl-bitprecise \
-setprop cpa.predicate.encodeFloatAs=FLOAT \
-setprop analysis.checkCounterexamples=true -setprop counterexample.checker=CBMC \
-setprop cpa.forcedCovering=cpa.predicate.PredicateForcedCovering
```

公共参数：`-heap 5000M -noout -64 -timelimit 170s -stats -spec <ALL.prp> <task>`；外层以 180s 强杀兜底，cgroup 内存 6000MB。

### 2.4 判定与统计

- 结果取自日志 `Verification result: TRUE/FALSE/UNKNOWN`；外部超时记 `timeout`，`OutOfMemoryError`/cgroup kill 记 `memout`，启动异常记 `error`。
- 安全/错误以文件名 `_true-unreach-call` / `_false-unreach-call` 为 ground truth；同时用论文原始结果做独立对照。
- 运行时间：用 CPAchecker 自报的 `Total CPU time`；外层墙钟另记，用于判断容器开销与兜底超时。**CPAchecker 的 `-timelimit` 计的是 CPU 时间**，k-induction 的并行分析可用 2 核，所以会出现“墙钟 80s 已达到 170s CPU 时限”的情况。

## 4. 错误轨迹分析

**任务**：`ldv-commit-tester/m0_false-unreach-call_drivers-hwmon-s3c-hwmon-ko--130_7a--af3071a-1.c`
**属性**：`CHECK( init(main()), LTL(G ! call(__VERIFIER_error())) )`
**算法**：BMC（k 从 1 起递增），日志确认 `Property violation (__VERIFIER_error(); called in line 1297)`，且 CPAchecker 用 CBMC 复核了该轨迹（`Error path found and confirmed by counterexample check with CBMC`）。

### 4.1 轨迹（`Counterexample.1.txt` 末段，行号为预处理后源码行号）

```
line 1213: main → s3c_hwmon_probe(var_group1)
line 1091: s3c_hwmon_probe → s3c_hwmon_create_attr(&dev->dev, pdata->in[i], ...)
line 974:  s3c_hwmon_create_attr → ldv_device_create_file_5(dev, &attr->dev_attr)
line 1278: ldv_device_create_file_5 → ldv_device_create_file_dev_attr_of_sensor_device_attribute(attr)
line 1368: [ldv_call_dev_attr_of_sensor_device_attribute == 0]
line 1369: ldv_count_2 = ldv_count_2 + 1;          // 0 → 1
line 1370: ldv_call_dev_attr_of_sensor_device_attribute = 1;
line 1371: [!(ldv_count_1 >= ldv_count_2)]         // 0 >= 1 为假
line 1374: ldv_error()
line 1297: ERROR: __VERIFIER_error();
```

### 4.2 根因

- `ldv_count_1` 由 `ldv_sysfs()` 递增（第 1353 行），代表“sysfs 已初始化”这一环境事件；该路径上 `main` 调用了 `ldv_initialize()`、`s3c_hwmon_init()` 和 `s3c_hwmon_probe()`，但**从未调用 `ldv_sysfs()`**，故 `ldv_count_1 = 0`。
- `ldv_device_create_file_dev_attr_of_sensor_device_attribute()` 在第一次被调用时把 `ldv_count_2` 加到 1，然后要求 `ldv_count_1 >= ldv_count_2`，否则调用 `ldv_error()`。
- 于是 `0 >= 1` 失败，进入 `ERROR:` 标签并调用 `__VERIFIER_error()`。

这是 LDV 基准中典型的**调用顺序违规**：驱动在 sysfs 尚未就绪时创建 `device_attribute`。它不是内存越界，而是“API 使用顺序”被 LDV 环境模型显式编码成 `ldv_error()`。本次 BMC 在 7.04s CPU 内报 FALSE；从 `main` 到错误点是一条很短、无需循环不变式的路径，`main` 中的 `__VERIFIER_nondet_int()` 选择 `case 0` 即可触发 probe。

### 4.3 轨迹解读的注意点

- `Counterexample.1.txt` 前 900 多行是 CFA 初始化时对 typedef/struct 的“声明边”，不是真实执行路径；真正的语义路径是最后从 `main` 到 `__VERIFIER_error()` 的 10 余条边。
- 轨迹中的 `line 1213` 等是**预处理后文件**的行号；原始 `.c` 的行号会偏移，报告引用时以轨迹文件为准。
- `ldv_count_1/2` 是 LDV harness 插入的模型变量，不是 Linux 驱动本身的变量；解释时不能把它们说成内核状态。


## 5. 算法结果差异案例

**任务**：`ldv-linux-3.4-simple/32_1_cilled_true-unreach-call_ok_nondet_linux-3.4-32_1-drivers--media--rc--keymaps--rc-npgtech.ko-ldv_main0_sequence_infinite_withcheck_stateful.cil.out.c`（C2 层）

**论文结果**：BMC 在 900s 内超时（913.5s CPU，inconclusive）；k-induction 6.9s 证安全；谓词抽象 6.8s；Impact 6.7s。

**本实验实测**：

| 算法 | 结论 | CPU 时间 | 关键日志证据 |
|---|---|---|---:|
| BMC | UNKNOWN（时限） | 173.57s | 迭代 31572 次；`maxLoopIterations` 被推到 1050 后命中 `CPU-time limit of 170s` |
| k-induction | TRUE | 6.14s | 论文 CSV 记录该任务 k=1；本实验日志未直接打印归纳步 k；不变式生成器迭代 42 次 |
| 谓词抽象 | TRUE | 6.72s | `Number of refinements: 1`；迭代 85 次 |
| Impact | TRUE | 13.64s | `Number of refinements: 1`；迭代 87 次；forced covering 0 次 |

### 5.1 这不是“结论冲突”

四种算法对 ground truth 没有分歧：该任务文件名是 `_true-unreach-call`，凡给出结论的运行都报 TRUE。差异在于 **BMC 无法终止**，其余三种能终止并给出正确证明。因此不能把它写成“BMC 认为是错的”，只能写成“BMC 在给定资源内没有给出结论”。

### 5.2 BMC 为什么不行

- BMC 的配置是 `cpa.bounds.maxLoopIterations=1` + `INCREMENT`：它把循环展开 k 次，检查错误位置的可达性；若不可达，就增大 k 继续。
- 对**无界**循环，BMC 只有在“前向条件检查”能证明继续展开不会产生新状态时，才能安全地停止并宣布 TRUE。该驱动的循环由 LDV 环境模型驱动，状态空间不由一个小的常量上界封闭。
- 于是 BMC 的 k 一路上升，公式规模与 SMT 时间持续增长，直到触及时限。它的 `UNKNOWN` 不是“程序安全”的证据，只是“在 k 和时间内没找到错误”。

### 5.3 k-induction 为什么能行

- k-induction 先跑与 BMC 相同的基例；基例在小时限内未发现错误后，转入归纳步：从循环头开始展开 k+1 次，检查“前 k 次的可达错误状态集合”是否蕴涵“前 k+1 次的可达错误状态集合”。
- 若蕴涵成立，则不需要继续展开——这正好补上了 BMC 缺失的“无界”推理。
- 本次运行的配置还并行启动了区间域不变式生成器（`analysis.useParallelAnalyses=true`，`invariantGeneration-no-out.properties::supply-reached-refinable`），用辅助不变式强化归纳假设。日志显示不变式生成器迭代 42 次；论文 CSV 记录该任务的 k=1。需要说明：本实验日志里的 `Bound k: 1` 属于 Invariant Generation 统计段，不是归纳步 k 的直接证据，因此这里只把“论文记录 k=1 + 6.14s 内完成”作为量级证据，不声称本实验独立测出了 k。

### 5.4 谓词抽象 / Impact 为什么也能行

- 两者都是 CEGAR：先构造一个可能过近似（over-approximation）的错误路径，若路径不可行，就用 Craig 插值细化精度（谓词抽象把插值谓词加入显式精度；Impact 直接把插值写到 ARG 状态上，属于惰性抽象）。
- 对这类指针/复杂数据结构密集的驱动，很多操作对安全性无关；抽象技术可以快速把它们“抽象掉”，而区间域不变式生成器反而可能被无关的指针算术拖慢（论文对 DeviceDrivers 类别的解释）。
- 本任务只有 **1 次细化**：谓词抽象 6.72s / 迭代 85 次，Impact 13.64s / 迭代 87 次。也就是说，两者都在第 1 次插值后即证明安全，没有经历“反复反例—细化”的长循环。Impact 这次反而比谓词抽象慢一倍，说明“惰性”并非在所有任务上都占优。

### 5.5 反向案例：BMC 的互补优势（C3 层）

`ldv-linux-3.7.3/main1_false-unreach-call_drivers-vhost-vhost_net-ko--32_7a--linux-3.7.3.c` 在论文中只有 BMC 在 72.3s 内找到错误；k-induction 在 401.5s 后内存耗尽，谓词/Impact 在约 125s 后内存耗尽。原因：BMC 一旦在某个 k 找到可满足的错误公式就立即停止并报告，不需要构造安全不变式；而另外三种算法会先尝试证明/抽象，在“错误很深、抽象很贵”的任务上反而先耗尽资源。这体现了四算法的**互补性**，也是论文主张 portfolio 而非单一算法的原因。

**本实验实测**：BMC 在 31.47s CPU 内报 FALSE（`__VERIFIER_error()` 在预处理后第 11626 行）；k-induction、谓词抽象、Impact 均在 28.8–43.8s 墙钟时被 6000MB cgroup 杀死（exit 137，日志尾部 `OOM_KILLED_BY_CGROUP`）。

所以“BMC 独解”在本环境完整复现。注意两点：
- 本实验 6000MB 上限低于论文 15GB，OOM 会更早发生；但论文在 15GB 下这三者本来也是 OOM/超时，故方向一致。
- BMC 的 31.5s 比论文的 72.3s 快，因为本实验没有像论文那样把进程限制在 2 核，且宿主 CPU 更新；这不影响“谁给出结论”的定性结论，但绝对时间不能与论文逐秒对比。


## 6. 效度威胁与自我审计

1. **模拟器倍率没有想象中大，但仍不可逐秒对比**：在选定的轻/中任务上，k-induction 最慢 53.9s CPU（论文 52.7s）、谓词/Impact 最大 12.5/13.6s（论文 ~10.8/13.9s），说明 amd64 模拟层没有数量级失真；但宿主是更新的 Apple Silicon、未限 2 核，BMC-vhost 31.5s 就明显快于论文 72.3s。结论只做“谁给出结论”的定性比较。
2. **内存上限远低于论文**（6000MB vs 15GB）：C3 的 k-ind/谓词/Impact 在 28.8–43.8s 就被 cgroup 杀死，而论文分别在 401.5s/约 125s 才 OOM。方向一致，但 OOM 时点不可比；若某任务在本环境 OOM、论文却能解，必须单独标注，不能算作算法失败。
3. **超时 170s CPU vs 论文 900s CPU**：本实验只对“论文在 ≤72s 内给出结论”的任务期待复现；C2/C4 中论文本身超时的任务，本实验也超时，方向一致。对论文中 100–900s 才解出的任务，本实验会提前判超时，故不能用本实验的 timeout 数估计论文的成功率。
4. **分层抽样偏差**：22 个任务中 11 个是刻意挑的“BMC 失败”或“BMC+k-ind 失败”任务，故 BMC/k-ind 的成功率不可外推；全类别统计见 §3.4。88/88 与论文一致也部分由抽样设计保证，不能当作独立验证。
5. **单次运行**：未重复 3 次，无法给置信区间；时间差异 <10% 不解读。
6. **版本漂移**：论文正文写 `cpachecker-1.6.8-vstte16`，结果 CSV 元数据写 `1.6.1-svn 22870`，实际 jar 自报 `1.6.1-svn 23022`；本报告以实际运行的 23022 为准。
7. **最脆弱的假设**：2016 年原生 MathSAT5 在 amd64 模拟层下行为与原生一致。已用 `example-safe.c` 冒烟测试验证可加载并给出 TRUE，且 70 个结论全部正确，但未验证大规模公式下的数值一致性。
8. **已修正的实现缺陷（审计记录）**：初版 runner 把日志文件名截断到 150 字符，导致同一 leds 任务的谓词/Impact 两个运行复用了试点日志（`wall=0.0s` 的 cached 记录）。已改为“任务 SHA1 前缀 + basename”并定向重跑；最终矩阵中无 cached 记录。
9. **BMC 的一个非典型终止**：w1_smem 的 BMC 在 MathSAT 原生 `msat_solve` 调用中命中 170s CPU 时限，CPAchecker 等待 10s 后强制终止，日志没有 `Verification result`。按“命中时限”归为 timeout，而不是算法错误；这一条不计入假阳性/假阴性。

## 7. 结论

1. **复现有效**：在 22 个 DeviceDriversLinux64 任务、88 次运行中，四种算法的 outcome 类别与论文 88/88 完全一致；70 个给出 TRUE/FALSE 的运行全部与 ground truth 一致，没有假阳性/假阴性。这说明“2016 原版 CPAchecker + MathSAT5 + 论文四条命令”在本容器环境中被正确复现。
2. **BMC 的边界是结构性的**：在 10 个 BMC 超时的安全任务上，以 npgtech 为例，BMC 最后一条展开界调整日志为 1050，仍未能终止，最终 UNKNOWN；它没有报错，只是不能证明 ∀k。相反，BMC 在 vhost 这类“浅错误”任务上 31.5s 就找到反例，而另外三者被 OOM 杀死——这正是 BMC 的互补价值。
3. **k-induction 不是万能**：它在本样本中 16/22 给出结论，但在 C4 的 5 个指针/复杂数据结构密集任务上全部超时；这与论文对 DeviceDrivers 类别的解释一致——区间域辅助不变式生成器不适合这类程序。
4. **两种抽象都能覆盖大部分安全任务**（各 21/22），但“惰性”不总是更快：npgtech 上谓词抽象 6.72s、Impact 13.64s，且都只需 1 次细化。把 Impact 当成谓词抽象的严格升级版是错的。
5. **实践含义**：四算法是互补而非替代关系。BMC 适合找浅错误/有界循环；k-induction 适合状态机式、归纳不变式容易表达的任务；谓词抽象/Impact 适合指针与数据结构复杂、但对安全性大部分无关的驱动。选择算法应看任务结构，而不是只看总体排行榜。
6. **本实验的边界**：6000MB/170s CPU 的资源上限、单次运行、分层抽样，决定了它只能验证“机制与方向”，不能给出 DeviceDrivers 类别的总体成功率；后者应以论文的 2120 任务全量数据为准（§3.4）。
