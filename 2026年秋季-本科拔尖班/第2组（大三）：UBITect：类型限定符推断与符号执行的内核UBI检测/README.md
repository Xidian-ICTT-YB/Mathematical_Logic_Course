## 任务简介

本项目复现 UBITect 的两阶段未初始化使用检测流程：

1. 第一阶段使用流敏感的类型限定符推断生成潜在 UBI 候选和路径探索指导；
2. 第二阶段使用欠约束符号执行搜索可行性路径，并由 SMT 求解器判断路径条件与未初始化条件能否同时满足。

项目完成了官方 `backlog.c` 教程，并对真实历史缺陷 `1a92b2b`、八个历史案例和 Linux 4.14 输入准备进行了审计。

## 工具搭建后的主要思考

1. **工具链复现的主要成本来自环境一致性。** LLVM 7、BBTag、修改版 KLEE 和 Z3 之间存在明确的构建顺序与版本依赖。旧版 Ubuntu、重复构建 LLVM、KLEE 查找系统库等问题，都会直接影响能否复现，而不只是代码本身能否编译。

2. **两阶段设计的核心是分别处理“规模”和“精度”。** 第一阶段接受一定近似，以较低代价把全内核缩小为少量候选；第二阶段再对候选做路径条件验证。两者不是简单的先后调用，而是由限定符分析生成 `avoidlist`、`mustlist` 等路径指导，减少符号执行的搜索空间。

3. **“模型内可满足”不等于真实环境可触发。** KLEE 和 Z3 只能在当前程序模型中判断路径是否满足。外部函数缺少函数体、内联汇编、线程与锁语义和资源预算都会使模型不完整，因此结果应区分为确认、候选、超时、不支持和未解析。

4. **复现报告必须区分模型结论与真实缺陷结论。** `backlog.c` 能稳定展示工具流程，`1a92b2b` 能证明工具在真实代码上产生候选，但缺少见证输入时不能写成完整确认。八历史案例的统计也不等同于漏洞数量。

5. **路径剪枝的价值主要体现在规模上。** 只要避开“会初始化变量”或“无法到达使用点”的基本块，就能提前终止整棵后续路径。这个机制是 UBITect 能够把轻量静态分析与昂贵符号执行结合起来的关键。
